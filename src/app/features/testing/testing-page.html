Testing con Vitest

Prueba comportamientos de Angular 22 con Vitest, TestBed y laboratorios de Angular Atlas.

Qué probar y con qué herramienta

  • Unitaria: verifica una pieza aislada, como la comparación de dos números.
  • Integración: verifica piezas que colaboran, como una ruta, su resolver y el componente que presenta el libro.
  • End-to-end: recorre el flujo completo en la aplicación desplegada o en un entorno equivalente, desde guardar un libro hasta volver a consultarlo.

Jasmine ofrece una API de pruebas y Karma ejecuta la suite en navegadores. El runner Vitest del CLI de Angular usa Node y jsdom por defecto. Los spies se crean con vi.spyOn() o vi.fn().

describe() agrupa casos, it() declara un comportamiento y expect() verifica el resultado. beforeEach() prepara cada caso y afterEach() limpia sus recursos.

Laboratorio A · Assertions

Prueba el contador con 0, 3 y 4. Compara qué pasa con los límites estricto e inclusivo. assertions.spec.ts verifica la lógica de la simulación con Vitest.

Laboratorio B · Componentes y Signals

TestBed prepara el entorno de Angular y crea el componente standalone. ComponentFixture da acceso al componente y a su DOM. detectChanges() fuerza una actualización y whenStable() espera el trabajo pendiente que Angular registra.

En seat-picker.spec.ts, la cantidad renderizada refleja el signal(). El precio y los asientos restantes verifican computed(). Prueba en el laboratorio el estado inicial, el aforo completo y el reinicio.

Laboratorio C · Dependency Injection y mocks

Angular resuelve el token del servicio a través del inyector. useValue sustituye su implementación en la prueba. vi.fn() permite programar resultados y comprobar llamadas. vi.spyOn() observa o sustituye un método de una instancia existente.

Laboratorio D · HTTP

En el laboratorio HTTP, compara una búsqueda vacía con una búsqueda válida y cambia el término rápidamente. Para reproducir esos estados en la suite, HttpTestingController captura la petición de BooksApiService y recibe la respuesta que le indica el test.

Configura provideHttpClient() antes de provideHttpClientTesting(). En books-api.service.spec.ts, flush() simula datos, un resultado vacío o respuestas 404 y 500. error(new ProgressEvent('error')) simula un fallo de red con estado 0. Al cambiar de consulta, la prueba de switchMap() comprueba que la anterior queda cancelada.

Laboratorio E · Router

Abre el catálogo filtrado por Angular, abre un libro y luego prueba salir del editor de notas con cambios pendientes.

provideRouter() instala la configuración real. RouterTestingHarness navega y expone el DOM de la ruta. En las pruebas de routing, CanMatch selecciona una ruta alternativa, CanActivate permite o bloquea la entrada y CanDeactivate consulta un doble de confirmación. El resolver usa el parámetro :id para cargar el libro o redirigir al catálogo.

Laboratorio F · Formularios

En Formularios, compara las pestañas Reactive Forms y Signal Forms. Escribe un título corto, sal del campo y luego intenta guardar dos veces. Prueba también el ISBN registrado 978-0-13-235088-4.

En Reactive Forms, consulta control.invalid, control.dirty y control.touched. En Signal Forms, lee field().invalid(), field().dirty() y field().touched(). El evento input aplica la edición del usuario y blur marca el campo como tocado. forms-page.spec.ts prueba validación, envío, concurrencia y errores.

Asincronía con Angular Zoneless

Usa async y await para promesas. Simula una respuesta rechazada con mockRejectedValue() y usa una promesa controlada para verificar un estado pendiente. Para un debounce, avanza el reloj virtual de Vitest y verifica cuándo se invoca el callback.

Restaura spies y temporizadores en afterEach(). Si el reloj virtual intercepta el planificador de Angular, avanza las tareas correspondientes antes de esperar la estabilidad. Simula las dependencias externas y comprueba cambios visibles, errores y límites.

Cobertura

Ejecuta estos comandos en el proyecto. El informe de cobertura se genera desde la suite del CLI. 

npx ng test --watch=false
npx ng test --watch=false --coverage
  • Líneas y sentencias: muestran qué partes del código se ejecutaron.
  • Funciones: muestran qué funciones se invocaron.
  • Ramas: muestran qué caminos de una decisión se tomaron, como éxito, lista vacía y error.

Una línea ejecutada puede carecer de una comprobación de su resultado. Abre el informe HTML y prioriza las ramas sin probar que afecten al usuario, como una navegación bloqueada o un fallo al guardar.

Consulta las guías oficiales de Testing de Angular, Signal Forms y cobertura.
