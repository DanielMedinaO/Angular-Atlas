loadComponent() frente a loadChildren()

Elegir el límite de carga diferida
APIQué cargaCuándo usarla
loadComponent()Un componente standalone.Una pantalla independiente y sencilla.
loadChildren()Un conjunto de rutas.Una funcionalidad con varias páginas y navegación propia.

Ambas APIs son lazy: el código se puede separar en chunks y solicitar al navegar. Las rutas declaradas directamente en la configuración raíz son eager. Este feature usa loadChildren() para mantener junto el grafo de rutas de Routing y cargar las páginas hijas bajo demanda.

Catálogo Notas

Resolver: preparar datos antes de activar

Para el detalle, bookResolver busca el libro localmente antes de activar BookDetail. El Router espera el resultado: el componente no se muestra en un estado intermedio sin libro. Esto evita una vista incompleta, a cambio de retrasar su activación hasta que la resolución termine. Un ID inexistente devuelve un RedirectCommand al catálogo. No hay peticiones HTTP en este laboratorio.

Guards de navegación

Cambia las decisiones y prueba estas rutas controladas. La demostración no implementa autenticación ni reemplaza la autorización del servidor.

Diferencias entre guards
GuardDecisiónUso habitual
CanActivatePermitir activar una ruta ya seleccionada.Controlar el acceso a una vista.
CanMatchPermitir que una configuración participe en el matching.Elegir entre configuraciones o variantes de ruta.
CanDeactivatePermitir abandonar la vista actual.Advertir por cambios sin guardar.
ResolvePreparar datos antes de activar.Entregar datos listos a una vista.

Un guard ejecutado en el navegador mejora la navegación, pero nunca sustituye la autorización del backend. Si un guard necesita redirigir, devuelve un UrlTree o RedirectCommand, en vez de iniciar otra navegación como efecto lateral.

CanDeactivate y cambios pendientes

El editor usa Signals para comparar el borrador con la última versión guardada. Su guard se evalúa en cualquier navegación del Router, incluida la navegación del historial Atrás y Adelante. El MVP usa window.confirm, un diálogo nativo que no permite adaptar estilo, contenido ni gestión de foco. En producción puede reemplazarse por un diálogo accesible con nombre, foco inicial, cierre por Escape definido y restauración del foco.

Preloading: decidir cuándo descargar

Comparación de carga y precarga
EstrategiaComportamientoCoste
EagerIncluye la ruta en el bundle inicial.Inicio inicial mayor; navegación posterior inmediata.
Lazy sin preloadingDescarga al visitar la ruta.Bundle inicial menor; primera navegación espera el chunk.
NoPreloadingNo descarga rutas lazy antes de visitarlas; es el comportamiento predeterminado.Menor uso de red anticipado.
PreloadAllModulesPre-carga rutas lazy tras la navegación inicial.Interacciones posteriores más rápidas; más tráfico y uso de datos.
Estrategia personalizadaPre-carga solo rutas marcadas.Permite equilibrar importancia y coste.
 
{{ preloadingSnippet }}

No activamos PreloadAllModules globalmente: primero conviene medir el tamaño de los chunks y el patrón de uso. En DevTools, abre la pestaña Network y filtra por .js; compara las solicitudes iniciales con las que aparecen al navegar y comprueba en Sources o Coverage qué código pertenece a cada chunk.
